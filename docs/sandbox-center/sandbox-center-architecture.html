Sandbox Center / Architecture Blueprint
2026-11-09 · design v1.9 · docs/sandbox-center

一个任务一个受保护环境；文件可恢复，进程不可复活

沙箱中心把环境分配、租约、执行、文件保存和回收收敛成一条可对账的链路。当前完成设计契约与阶段 1a 控制边界实测，运行实现尚未开始。

01 / 全局架构

控制面定策略，执行面只认已绑定的租约

横向四层：接入、控制面、执行面、工作区与数据。左侧是平台治理边界，右侧是外部系统。Agent 客户端不持有 Kubernetes 凭证，也不直接连接 Pod IP。

02 / 生命周期

先写事实，再产生副作用

一次任务从幂等申请到物理删除，共五个可查询阶段。保存失败不是异常分支，而是阻止删除的正常状态。

三个版本号不能混用

  • holderRunEpoch：Agent 平台的一次 worker 执行权，由 Run 库维护。
  • fencingToken：工作区写权世代，由沙箱中心维护。
  • admissionEpoch：Runtime 本地准入批次，由 Guard 维护。

Ready 的判定

Pod Running 和端口打开都不够。必须同时满足：实例身份与 boot ID 一致、Runtime 能力探测通过、工作区恢复到指定版本、只读资产就位、基础命令与文件自检通过。

03 / layerfs 工作区

用分层替代整卷克隆，用增量替代全量备份

只作用于 EphemeralCopy（自动 Coding）。PersistentVolume 仍直接挂载，不用叠加层。

为什么只给 EphemeralCopy 用

持续开发承诺的是“用户直接看到的持久卷语义”。叠加层会引入 lower/upper 映射、whiteout 和挂载状态，让 git status、权限与工具链排障变复杂，也容易让用户误以为底层文件已被修改。自动 Coding 需要的是快速得到干净副本、任务结束即丢弃，正好匹配分层模型。

04 / 恢复与保存保护

恢复只承诺文件，保存失败阻止删除

三种恢复等级描述 Pod 丢失后可恢复的文件范围。任何等级都不恢复进程、内存或外部副作用。

必要保存失败 = SaveBlocked

  • 停止用户执行，保留文件、工作区占用和实际配额。
  • 时间到期、空闲回收、配额压力、控制面重启都不解除保护。
  • 释放 API 没有 force 参数；放弃使用独立授权与审计。
  • 任务拥有者确认放弃，不等于保存成功，也不等于数据已删除。

谁有权做什么

  • Agent 平台：显式触发检查点、提交释放、在业务界面发起放弃确认。
  • 执行 worker：只能在受限保存权限内重试冻结范围，不能放弃。
  • 沙箱中心：验证静止、保存、发布和对账，不推断业务阶段。
  • 管理员：只在既有跨用户授权范围内处理异常。
05 / Worker 接管

新 worker 先只读对账，再申请新租约

首版不移交活动租约。旧 epoch 的写权限不能被继承，旧命令也不能被重复启动。

07 / 已定决策

六项已确认，进入契约与阶段 2 准备

2026-11-09 已拍板，完整记录见 ADR-0005。前两项决定 layerfs 的实施路径；其余四项已写入契约和验收边界。

挂载权限：节点侧预挂载 已定

叠加挂载由节点侧 Workspace Materializer 完成，经 hostPath 和 mountPropagation 暴露合并视图。Guard 保持 SETUID/SETGID，不新增 CAP_SYS_ADMIN，只校验 digest、只读性与挂载事实。

落地前提：目标 RuntimeClass 先跑 overlay、mountPropagation 和 hostPath 策略探针。节点侧不可行时退到 Pod 内 fuse-overlayfs，仍需单独验收；Pod 内内核 overlayfs 加 CAP_SYS_ADMIN 不作为首版方案。

基础层：只读 PVC 为真源 已定

每个基础层按内容 digest 对应一个只读 PVC，由 Layer Materializer 从对象存储或仓库快照生成。节点侧只读挂载后同节点同 digest 共享 lower；跨节点重新挂载同一 PVC 获得一致内容。

验收边界：基础层物化和挂载记录为 Preparing 的独立阶段；digest 或只读校验失败不得进入 Ready。镜像卷、节点本地缓存后续复用同一 BaseLayerRef 契约。

增量格式：OCI layer 风格 已定

检查点由 manifest 和 upper 增量层组成。manifest 记录基础层 digest、增量层 digest、覆盖范围、一致性级别、生成时间和工具版本；增量层用 OCI layer 兼容的 tar 表达新增、修改、删除和 opaque 目录。

恢复语义：先物化新的只读基础层，再把增量层应用到新的可写层，不依赖原 Pod、原节点或原可写层；两份对象都按内容寻址并校验 digest。

静止证明：固定证据集合 已定

ApplicationConsistent 必须同时满足：准入屏障关闭新写入与新输入；已受理操作排空；沙箱 cgroup 除 Guard/execd 外无用户进程；无仍可写的文件描述符或在途写入；合并视图 syncfs 成功；基础层 digest 与挂载事实未变化。

失败处理：任一项无法确认即明确失败。只有调用方显式声明 CrashConsistent 且 Profile 允许时才降级，服务端不得静默改级。

WarmPool：首版不按 digest 分池 已定

公共 WarmPool 只预热空工作区，认领后才物化基础层，因此 T_ready 包含基础层就位时间；这是首版接受的成本。当前 poolKey 不加入基础层 digest，避免库存按仓库版本碎片化。

后续触发条件：高频基准被证明值得专属库存时，只为少量 Profile 增加带 digest 的池键和预物化策略；池键格式变化必须版本化，新旧池不得互相认领。

契约：公开 LayeredWorkspace capability 已定

公开 SDK 新增 CapabilityLayeredWorkspace。Profile 声明非空 LayeredWorkspace.Engine 时必须同时声明该能力；实例就绪时还要核对实际挂载事实，不能只信声明。

调用方收益：可以判断恢复耗时来源，并避免把未验证的分层工作区当成普通目录；能力缺失时仍返回 CapabilityUnsupported。
