# 企业级 Agent 沙箱管理中心

日期：2026-10-22  
文档状态：内容与测试入口已确认的实施规格  
目标项目：FlyTOmeLight/agentic-kit-api  
分流标签：ready-for-agent

发布记录：[GitHub Issue #7](https://github.com/FlyTOmeLight/agentic-kit-api/issues/7)

## Problem Statement

企业 Agent 平台需要为自动 Coding、持续开发、脚本分析和浏览器任务提供可靠的执行环境。调用方希望提交任务后知道环境何时可用、命令是否执行、修改保存在哪里，以及断线或节点故障后能恢复哪些数据，而不必分别集成 Kubernetes 和各类沙箱产品。

这些场景对环境复用、文件保存和进程寿命的要求不同。把它们绑定为同一个“会话”或统一 TTL，会导致错误共享工作区、重复执行命令、丢失未交付修改，或长期占用无人管理的资源。仅有容器运行状态或 HTTP 成功响应，也无法证明任务结果、文件发布和资源回收已经完成。

平台还需要支持多种 Sandbox Backend。选用 AIO 等组合环境或专用执行组件，应由任务能力与隔离要求决定，而不应迫使上层 Agent 使用不同的生命周期协议。CLI Agent 的厂商会话、恢复与事件解析仍应由 Agent 平台管理。

本需求建设一套完整的新沙箱中心，不以改造现有 sandboxmanager、迁移历史数据或兼容旧接口作为交付目标。

## Solution

提供以 Kubernetes 为计算底座的 Headless Server，通过统一 HTTP API、Go SDK、SSE 和按需启用的 WebSocket 服务调用方。平台发布经过验证的不可变场景配置 Profile；调用方选择已授权版本，即可申请环境、等待就绪、执行命令、访问文件、保存工作区结果并释放资源。

一次完整业务流程为：Agent 平台登记任务和会话，申请指定 Profile 的沙箱，等待环境与工作区 Ready，取得写租约，执行并读取结果，在业务阶段显式保存检查点，确认必要保存完成后释放。控制面重启、响应丢失和租约过期均有可查询的持久事实。无法确认的副作用保留为 Unknown，由对账确定结果。

自动 Coding 默认在任务内复用干净临时环境，恢复到最近确认发布的检查点；持续开发使用持久工作区，在隔离旧写者后恢复文件。必要保存失败时停止执行并保留待保存数据。任务拥有者可以在业务界面明确确认放弃自己的未保存结果，无需管理员代办；执行 Worker 不因此获得放弃权限。

隔离等级由 Profile 固定，默认 Hardened。Standard 仅向平台验证过的受控任务开放，容量不足或兼容性问题不触发自动降级。

## User Stories

1. 作为 Agent 平台开发者，我希望通过同一 SDK 使用不同沙箱 Backend，以便业务逻辑无需理解厂商协议。
2. 作为任务发起者，我希望查询自己有权使用的 Profile 和能力，以便选择满足任务要求的环境。
3. 作为平台维护者，我希望发布不可变的 Profile 版本，以便新配置不改变已经运行的任务。
4. 作为任务发起者，我希望指定任务、会话或工作区的授权作用域，以便后续调用只复用属于该作用域的环境。
5. 作为 Agent 平台开发者，我希望重复申请返回同一结果，以便响应丢失不创建多个沙箱或重复占用配额。
6. 作为任务发起者，我希望看到排队、准备和失败阶段，以便判断当前等待原因。
7. 作为任务发起者，我希望取消尚未完成的申请，以便不再消耗无用资源。
8. 作为任务发起者，我希望只在工作区、权限和 Runtime 均就绪后收到 Ready，以便首次执行不会用来探测初始化状态。
9. 作为平台维护者，我希望维护不含用户数据和凭证的预热池，以便降低环境分配延迟。
10. 作为平台维护者，我希望多个控制副本不会重复认领或重复补池，以便库存和预算准确。
11. 作为任务发起者，我希望池为空时按明确策略冷创建、等待或失败，以便控制等待时间与成本。
12. 作为持续开发用户，我希望使用匹配自己持久卷的环境，以便不会挂载其他工作区或丢失已有文件。
13. 作为租户负责人，我希望排队、准备、运行、保留和保存阻塞均按实际占用计入配额，以便资源使用可解释。
14. 作为 Agent 平台开发者，我希望租约和执行期限可查询、可受限续期，以便长任务有明确的使用资格。
15. 作为工作区拥有者，我希望旧租约和迟到请求不能继续写入，以便新持有者不会遭到旧任务干扰。
16. 作为任务发起者，我希望断开输出连接不等于取消任务，以便网络中断后可以继续观察原执行。
17. 作为 Agent 平台开发者，我希望启动命令前先取得持久执行 ID，以便断线后能够查询实际执行事实。
18. 作为任务发起者，我希望看到退出码、超时、取消与未知结果的区别，以便不会把未确认操作当成成功或失败。
19. 作为 Agent 平台开发者，我希望结果不明的命令不被自动重放，以便避免重复提交外部副作用。
20. 作为任务发起者，我希望增量读取和补读日志，并明确知道输出缺口，以便正确判断任务过程。
21. 作为交互用户，我希望按需使用 stdin、终端、浏览器和预览，以便处理交互任务与人工接管。
22. 作为交互用户，我希望终端重连时仍只有一个合法写连接，以便输入不会交错或重复发送。
23. 作为任务发起者，我希望取消操作清理子进程和后台进程，以便任务停止后不再继续占用或修改资源。
24. 作为 Agent 平台开发者，我希望有界读取、写入和搜索工作区文件，以便控制数据量和访问范围。
25. 作为工作区拥有者，我希望文件路径、软链接和访问凭证不能越过授权边界，以便其他任务的数据保持隔离。
26. 作为多 Agent 任务开发者，我希望同一任务的子 Agent 使用独立 Git 工作树，以便减少分支、索引和未提交修改冲突。
27. 作为任务集成者，我希望子 Agent 的基准版本、修改与冲突可见，以便明确决定如何集成结果。
28. 作为平台维护者，我希望 Skill 和公共依赖缓存按固定版本只读提供，以便一个任务不能污染其他任务。
29. 作为 Agent 平台开发者，我希望在业务里程碑显式创建检查点，以便恢复点与任务进度一致。
30. 作为任务发起者，我希望检查点明确覆盖已跟踪、未跟踪和二进制文件等范围，以便知道哪些修改能够恢复。
31. 作为任务发起者，我希望未能静止全部写入者时得到明确失败，以便不会收到虚假的一致快照。
32. 作为自动 Coding 用户，我希望节点故障后恢复最近已发布检查点，以便在明确的数据边界上继续任务。
33. 作为持续开发用户，我希望恢复持久工作区前先隔离旧写者，以便不会出现双写破坏。
34. 作为 Agent 平台开发者，我希望文件恢复和进程恢复分别报告，以便自行核验 CLI 会话并决定是否建立新执行尝试。
35. 作为任务发起者，我希望任务结束时先确认必要保存，再清理环境，以便命令成功不会掩盖交付失败。
36. 作为任务拥有者，我希望必要保存失败后保留文件并停止任务执行，以便仍有机会取回未交付修改。
37. 作为运维人员，我希望查询保存阻塞原因、范围和当前尝试，以便定位积压并恢复保存。
38. 作为授权的保存 Worker，我希望租约过期后仍能重试冻结范围的保存，以便故障恢复不依赖重新开放执行权限。
39. 作为任务拥有者，我希望明确确认放弃自己的未保存结果，以便不再需要这些结果时自行结束保留。
40. 作为任务拥有者，我希望过期页面上的确认不能用于后来变化的数据，以便不会误删未经确认的修改。
41. 作为平台维护者，我希望普通 Worker 不能自动放弃结果，以便 Agent 的结束决策不会绕过用户的数据决定权。
42. 作为授权管理员，我希望在明确的跨用户权限范围内处理异常保留，以便解决无人可处理的积压并留下审计。
43. 作为任务拥有者，我希望放弃回执与实际删除分别可查，以便了解资源是否已经释放。
44. 作为平台维护者，我希望 TTL、GC 和配额压力都不能绕过保存保护，以便自动清理遵守一致的数据规则。
45. 作为安全负责人，我希望 Agent 生成或外部提供的代码默认进入 Hardened 环境，以便平台按已验证隔离等级运行任务。
46. 作为受控任务的维护者，我希望在平台验证和授权后使用 Standard Profile，以便满足明确的工具兼容性和成本要求。
47. 作为安全负责人，我希望凭证按租约、受众和服务范围授予，并在结束后撤销，以便任务不能取得平台长期密钥。
48. 作为安全负责人，我希望终端、浏览器、预览、日志和归档访问统一鉴权，以便不能通过直连地址绕过授权。
49. 作为 Agent 平台开发者，我希望自己管理 Codex、Claude Code、OMP 等 Runner 的版本、事件和会话恢复，以便沙箱服务保持通用。
50. 作为平台维护者，我希望重启后从持久状态继续对账，以便内存队列丢失不丢任务。
51. 作为运维人员，我希望看到分配、环境就绪、任务就绪和可交付时间的不同指标，以便准确定位慢在哪个阶段。
52. 作为验收人员，我希望同一组外部行为用例在两个 Runtime 上运行，以便确认能力声明和协议适配真实有效。

## Implementation Decisions

1. **服务与职责边界。** 沙箱中心负责通用环境、执行、文件、访问会话、工作区和资源事实。agentic-kit 负责 Agent 会话、模型循环、任务规划、CLI Runner、厂商事件、业务审批与业务续跑。CLI 会话及其 execution 映射不进入沙箱中心表模型。
2. **部署单元。** API 与 Reconciler 可在同一代码库中按进程角色部署；执行网关可按长连接负载独立扩容。Provider、Runtime Adapter、工作区与授权模块采用进程内职责边界，不默认拆为多个微服务。
3. **多 Backend。** Provider 管物理资源，Runtime Adapter 管环境内协议，Profile 发布验证过的组合。首组为 Kubernetes Provider、AIO Runtime Adapter 和 OpenSandbox execd Runtime Adapter。具体版本、镜像 digest 和能力必须在实施时锁定并验证；不把选型方向当作上游已兑现全部契约。
4. **物理身份。** 一个沙箱对应明确身份的 Pod，物理重建产生新代次。结合 Pod UID 与 Runtime boot ID 判断环境是否仍是原实例。采用受控 Pod 生命周期，避免自动替换被误认为原进程仍存活；同一物理资源只能由一个生命周期控制器管理。
5. **Profile。** Profile 身份包含所属租户、ID 和 revision，固定镜像、资源、能力、隔离、挂载、环境复用、文件保存与执行规则。关联策略按不可变版本解析。调用方只选择 Profile，并在公开上下界内调整允许的时长；作用域、工作区模式、保存策略和 Release mode 是一致性断言，不是自由覆盖项。
6. **隔离默认值。** 默认 Hardened，Standard 需要平台对受控任务范围的验证和授权。最低隔离要求只增加约束；较低要求不改变所选 Profile。运行时不可用、兼容性问题或容量不足不能触发自动降级，也不能默认授予 privileged。
7. **能力协商。** 有效能力取 Profile 声明、Adapter 实现、Runtime 固定版本验证结果和租户授权的交集。自主 Agent 基础能力覆盖命令、异步执行、增量输出、进程树取消和文件访问；PTY、浏览器、预览等按组合可选。缺失能力明确返回 CapabilityUnsupported。
8. **分配顺序。** 校验主体、授权、能力、配额与期限后处理申请幂等；Reuse 先检查作用域绑定实例，再认领完全兼容的 WarmPool，最后按 AllowCold、WaitForWarm 或 FailIfNoCapacity 处理容量不足。默认 AllowCold，但不绕过配额和截止时间。
9. **所有权。** Task、Session、Workspace 复用作用域由 Profile 固定；Session 是调用方的不透明作用域，不是沙箱管理的 Agent 会话。同一工作区同一时刻只有一个根写持有者。准备权由 acquisition 持有，Ready 时原子转为 lease，不能在准备期间发放第二份占用。
10. **WarmPool。** 公共库存只包含不带用户仓库、可写数据、凭证或浏览器登录态的干净实例。池键绑定物理配置、隔离、Runtime、模板和卷布局。认领后可准备仓库与受限身份，但不能给运行中的 Pod 任意替换静态 PVC。使用过的实例不回公共池；IdleBound 仍属于原授权作用域。
11. **库存控制。** 通过持久库存、短事务、版本条件和资源预算维护 minReady、maxReady、maxProvisioning 与空闲回收；控制循环核对实际 Pod，避免多副本重复补建。节点镜像缓存、干净 Pod 库存和已绑定工作区复用分别度量。
12. **Ready 与期限。** Ready 同时要求物理身份正确、Runtime 能力和认证通过、工作区及只读资源准备完成、受控网络和凭证可用、自检通过。准备期限、租约期限、硬执行期限、命令期限和空闲期限分别定义；HTTP 等待超时只结束本地等待。
13. **执行租约。** 普通实例写操作需要有效 LeaseProof、当前代次与 fencingToken，以及持有者权限和准入状态。申请与租约固定 holderRunEpoch，写入和续租验证可信当前 Run 领取。新 epoch 先对账和清理旧租约，确认停止与必要保存后再申请，不移交旧写权限，见 [Worker 接管协议](worker-handoff.md)。过期续租不能复活权限，日志读取不自动续租。fencingToken 证明当前写资格，不证明旧节点的实际进程已经停止。
14. **持久控制。** MySQL 保存业务与生命周期事实，Kubernetes 保存物理资源事实。Reconciler 持续对账，内存队列只负责唤醒。数据库事务不包含外部网络调用；资源创建按确定身份对账，外部响应丢失不能直接生成第二份资源。
15. **执行与未知结果。** Start 派发前保存执行 ID、请求身份和 Starting 事实。仅可信退出证据形成执行终态；无法确认是否执行时标 Unknown。Worker 处理权到期不授权重放命令；外部副作用不承诺 exactly-once。Argv 与 Shell 明确二选一。
16. **释放与迟到请求。** Release 先关闭准入，再处理 Pending、Starting、Running 和未知派发，停止进程、访问会话和凭证。Retain 也先清理进程，满足保存条件后进入 IdleBound；Destroy 满足条件后删除资源。无法证明旧执行停止时保持隔离与工作区占用。
17. **交互与输出。** SSE 使用平台资源序列与补读游标，缺口明确报告 OutputGap。日志归档持久化后再推进可见范围。stdin、PTY 输入和会话变更不自动重放；终端资源、连接与单写所有权分别管理。关闭本地流不等于 Cancel 或 Release。
18. **文件与子 Agent。** 文件操作限定授权工作区并约束大小、路径与软链接；条件写需要 Runtime 原子支持，不能对任意 Shell 写入宣称全局 CAS。可信同任务子 Agent 可在同 Pod 使用独立 Git worktree；worktree 不构成跨租户或敌对代码安全隔离，也不自动解决集成冲突。
19. **场景恢复。** 自动 Coding 默认 Task 内复用、EphemeralCopy、Checkpointed，任务结束后 Destroy。持续开发使用 Workspace、PersistentVolume、Persistent，释放后可 Retain，保留文件但停止原进程。没有已发布检查点时，不宣称恢复了任务修改；持久卷恢复必须先隔离旧写者。
20. **检查点触发与发布。** agentic-kit 按业务阶段显式调用 CreateCheckpoint；沙箱验证全部写入者静止，保存覆盖范围、manifest 和发布证据。ApplicationConsistent 无法满足时不得静默降级。仅已受理请求由 Reconciler 继续执行，无自主周期检查点与固定时间 RPO 承诺。
21. **必要保存保护。** Release 从固定 Profile 与冻结保存意图建立完整要求集合，包括尚未受理操作的缺口。旧检查点、空 ID 集合、资源终态或超时均不能替代本次保存。失败时进入 Draining/SaveBlocked，停止用户执行并撤销凭证，保留受限保存通道、文件与配额；进程停止无法确认时保持隔离。
22. **受限保存重试。** GetBlockedSave 返回当前完整确认快照。RetryRequiredSave 使用独立资源授权，在租约过期后只允许保存冻结范围，不恢复执行。终态 Failed 保留，由关联的新操作替代；Unknown 先对账，Pending/Running 不创建重复尝试。对应替代尝试成功后可满足原要求。
23. **拥有者确认放弃。** DiscardBlockedSave 验证业务系统认定的任务拥有者、可信用户确认或受限委托。普通 Worker token、请求体 userID 和确认布尔值不提供权限。管理员只在跨用户授权范围内使用同一精确处置流程，不设 force 绕过入口。
24. **处置范围与并发。** 确认绑定实例和工作区代次、冻结数据版本、释放操作、完整保存要求与快照修订。重试、数据变化、发布或处置修改共同版本；陈旧确认拒绝。放弃回执只豁免对应未满足要求，保留失败历史和已发布结果，不代表保存成功或删除成功。
25. **删除前置条件。** 放弃后仍须确认进程隔离，并对在途保存和发布完成对账或取得外部强制隔离证据；只提高数据库 epoch 不足以证明外部调用已停止。正常删除、GC、TTL、配额回收和故障清理遵守同一保存保护，不能用删除唯一数据副本作为常规停止进程手段。
26. **事务接口。** 沿用 AllocationStore、ExecutionStore、OperationStore、ReconcileStore、PoolStore、InstanceStore 等职责端口。BlockedSaveStore 以 GetBlockedSave、BeginSaveRetry、CompleteRequiredSave、ConfirmDiscard 原子维护保存保护与现有动作账本。普通检查点在纳入释放保护前仍正常完成；与 BeginRelease 并发时在共享锁序内确定归属。
27. **授权与外部系统。** Authorizer 统一认证、资源授权及 AuthorizeSaveRecovery。凭证、产物版本、对象存储、代码托管和业务归属沿用企业已有系统。保存恢复证据使用可信引用，不将可调用的密钥写入动作账本。模型、Git 和存储访问按具体 scope 授予，任务结束撤销。
28. **网络与访问。** 默认拒绝出站，再由 Profile 放行必要路径；域名控制由已验证出站代理或网络实现承担。终端、浏览器与预览均通过鉴权网关，不能把 Pod IP 或不可猜 URL 作为授权。命令退出和 stdout 不能证明完整工具审计或外部交付成功。
29. **公开 Go SDK。** 提供 12 个职责组、50 个 Client 方法，覆盖 Profiles、Acquisitions、Sandboxes、Leases、Executions、Files、Access Sessions、Worktrees、Checkpoints、Blocked Saves、Operations 和 Administration。公开模型使用标准库类型，内部适配器转换第三方类型。服务实现需交付实际 HTTP 客户端、路由及流实现，当前仅有声明。
30. **协议与错误。** JSON 使用 lowerCamelCase，时间采用 UTC RFC3339，公开时长为秒，可空事实用 null。HTTP 202 表示受理，命令、数据发布与清理分别查询。SDK 不因重定向、鉴权刷新、网络错误或 Retry-After 自动重放变更；以原身份和请求键查询。上下文取消只取消该次请求或等待。
31. **幂等身份。** 申请按 tenant/caller/requestKey，执行按 lease/requestKey，普通动作按 tenant/caller/action/target kind/id/revision/requestKey 去重。摘要包含有效语义参数和代次，排除传输凭据等非语义字段；相同键不同语义返回冲突。墓碑与保留期防止迟到请求产生新副作用。
32. **关系模型。** 采用 18 张表、517 个字段及逐列对应 Go Row。配置与分配包括 sandbox_profile_revision、sandbox_acquire_request、sandbox_instance、sandbox_lease、sandbox_reuse_slot、sandbox_workspace_binding、sandbox_warm_pool；配额包括 sandbox_quota_account、sandbox_quota_reservation；执行和操作包括 sandbox_execution、sandbox_action；文件状态包括 sandbox_worktree、sandbox_checkpoint；访问包括 sandbox_access_session、sandbox_access_ticket；事件和输出包括 sandbox_event_stream、sandbox_event、sandbox_output_segment。
33. **数据库约束。** MySQL/InnoDB 通过唯一约束、CHECK、短事务、条件更新和固定锁序维护归属及状态。无级联删除；跨表租户、代次与身份关系由事务校验。保存保护、重试关联、授权与放弃回执复用已有类型化 JSON 和动作账本，不另建审批表或 CLI 会话表。Profile 所属租户字段保留在关联记录中。
34. **数据编码与账本。** JSON 使用 schemaVersion/data 封装并按列和动作绑定具体类型；25 种公开 OperationKind 与 3 种内部动作分别映射。敏感凭证不进入 JSON、事件和普通日志。可空 SQL 与公开 DTO 分别建模；代次与序列不回绕，公开计数遵守 JSON 精度边界。
35. **配额与删除证据。** 公共库存预算与租户逻辑占用分别记账，认领时转换归属。保存阻塞、未知进程和未确认删除保持相关占用，Release 受理不提前归还实际容量。状态变更和生命周期事件在同一事务提交。
36. **CLI 接入。** 支持平台 Agent Loop 远程调用工具，以及沙箱内运行完整 CLI Agent 两种形态。agentic-kit 固定并验证 CLI 版本、参数、结构化事件和会话路径；断线先查原 Execution，需要恢复时核验文件与会话后创建新尝试。不得形成 CLI 把平台工具再次代理回自身的循环。
37. **可观测性。** 分别记录申请、认领、环境可用、工作区 Ready、执行、保存和实际清理的时间与原因。热池命中只影响部分阶段。初始目标是同集群、有空闲库存且无排队条件下 T_claim p95 不超过 1 秒；完整任务耗时按真实仓库和部署建立基线。

## Testing Decisions

1. **主验收入口（已确认）。** 使用公开 Go SDK 调用实际 HTTP 服务，沿 Acquire → Ready → Execute → Checkpoint → Release 跑完整业务流程。同一套用例参数化运行 AIO 与 execd，避免为每个内部模块分别制造一套只验证调用顺序的 mock 测试。
2. **判定标准。** 断言外部可观察结果，包括唯一分配、查询状态、退出结果、文件内容、授权拒绝、输出缺口、已发布对象与实际资源释放。数据库与 Kubernetes 观察用于核实副作用和隔离，不把 SQL 顺序、私有函数调用次数或 HTTP 200 当作验收本身。
3. **环境与必要测试边界。** 并发认领、配额、事务及重启使用真实 MySQL；物理隔离、卷挂载、进程树和网络策略使用测试 Kubernetes 集群及固定 Runtime 镜像。响应丢失、超时和故障窗口优先在已有 Provider、Runtime Adapter、WorkspaceDriver、ArtifactPublisher 和授权边界注入，不为测试增加无业务用途的生产接口。
4. **申请与库存。** 并发相同请求只分配一次；不同参数冲突；两个根 Run 不取得同一写租约；准备权不能被抢占；热池空时遵循容量策略；不匹配卷不能认领；使用过或准备失败的实例不回公共池；控制面在提交后退出仍可继续对账。
5. **Profile 与隔离。** 场景断言不匹配和越界超时在使用资源前拒绝；新版本不改变旧实例；Hardened 默认和 Standard 资格在发布及申请时生效；低 minimumIsolation、容量不足和工具不兼容不能降级。验证实际 RuntimeClass/CNI/CSI 行为，不只检查配置存在。
6. **执行与恢复。** 注入 Start 响应丢失、Worker 退出和数据库提交结果不明，确认不重复执行，未知结果可查。验证命令非零退出、超时、取消子进程、迟到 Start、过期心跳和旧 fence 拒绝；SDK 网络层也不得重放变更。
7. **日志与交互。** 断线重连从已消费序列补读；超出保留范围报告缺口；stdin 与终端输入响应丢失不重复发送；终端连接不产生双写；关闭输出流不取消远端执行；网关身份检查覆盖事件、归档、浏览器和预览。
8. **工作区与检查点。** 使用包含 tracked、untracked、binary、权限位和符号链接的真实仓库检查覆盖范围与恢复结果；测试并行 worktree 冲突和活动写者拒绝。直接 Shell/CLI 写入也纳入静止验证；没有显式请求不自主创建检查点，未发布不返回 Ready，不静默降低一致性。
9. **必要保存与重试。** 存储故障时关闭执行但保留文件与配额；TTL、GC、重启、空操作列表和旧检查点不能解除保护。覆盖未受理缺口、Failed 替代、Unknown 对账、正常检查点完成与 BeginRelease 并发，以及成功替代后不因原 Failed 永久阻塞。
10. **明确放弃。** 拥有者可以处置本人当前范围，其他用户和无处置权限 Worker 被拒绝；验证可信委托、管理员范围、陈旧版本、漏报保存要求、重复请求及并发重试/发布。回执不触发越界删除；在途发布未完成对账或隔离前不删除唯一文件副本。
11. **节点与控制故障。** 注入 Pod OOM、节点失联、API/网关/控制进程退出、Kubernetes 创建响应丢失、存储不可用和数据库不可用。旧写者未隔离前不重新挂载可写卷；恢复文件不合成进程续跑或外部操作成功；物理删除失败不提前归还容量。
12. **交付与性能。** 分别核对命令退出、日志完整性、检查点发布和产物交付证据；按相同仓库、资源、隔离与存储条件比较两个 Runtime 的读取、搜索、构建、长日志、取消和恢复。只在定义条件下评价 T_claim 目标，不推导完整任务秒级完成。
13. **现有测试先例。** 已静态核对 agentic-kit：sandboxmanager 测试覆盖申请参数、环境变量限制、Pod 模板、shell 转义、超时与输出映射；网络策略使用 Kubernetes fake 验证生成和漂移修复；鉴权测试验证未认证请求拒绝，SDK 使用自定义 RoundTripper 验证路径与编码；runner 使用 SQLMock 验证终态与 CAS 失权处理。可借鉴这些表驱动场景、协议断言及故障注入方式，但不能沿用旧 API 或调用方自由覆盖规格的语义。
14. **现有验证的边界。** 配套 Go 契约已完成编译、静态检查与模型映射检查，没有服务实现和行为测试。现有仓库的 fake/mock 测试不能证明真实数据库并发、跨副本恢复、CNI 隔离或远端进程停止。本次仅核对测试源码，没有重跑这些旧测试；新中心仍需完成上述公开入口验收。

## Out of Scope

- 旧 sandboxmanager 的升级迁移、历史表迁移、旧 API 兼容层及旧生产环境切换。
- 在本次规格整理中实现或部署服务、修改 agentic-kit 业务代码、安装运行时和执行集群变更。
- 模型路由、Agent 规划、对话持久化、CLI 原生会话表、业务审批、自动决定任务成功，以及自动创建 MR 或部署结果。
- IDE 内联代码补全引擎、完整 Web/IDE 产品界面；本需求提供它们可消费的服务接口与行为。
- 新建代码托管、对象存储、产物版本、密钥管理或独立审批平台。
- 任意镜像、Pod 配置、权限、Provider 与 Runtime 的自由组合；静默切换 Backend 或降低隔离等级。
- 把 worktree 当安全沙箱、恢复原进程内存、透明续跑所有 CLI 会话、自动重放未知命令，以及外部副作用 exactly-once 保证。
- 自主周期检查点、固定时间 RPO、超时后自动放弃未保存结果，以及无保存检查的 force 删除。
- 在没有目标环境证据时承诺全部可选 Runtime 能力、底层存储零丢失或统一任务耗时。

## Further Notes

- 本 Spec 汇总本轮完整设计与已接受决策。设计材料已定义完整 Go SDK、内部接口、SQL、Row 和动作载荷，实施需保持这些层面的语义一致。规格不是已经上线的能力清单。
- 明确确认的边界包括：CLI Runner 和 Agent 会话归 agentic-kit；Profile 固定场景策略；按场景区分恢复等级；业务显式触发检查点；必要保存失败阻止正常删除；拥有者可以明确放弃；隔离按 Profile 区分且默认 Hardened。
- 首组 Runtime 为 AIO 和 execd。目标集群、固定依赖版本、镜像 digest、RuntimeClass/CNI/CSI 组合与真实兼容性由实施验收确定，不从产品名称推断支持。租约、池水位和保留期属于发布配置，既有建议值不是所有场景的硬编码常量。
- 研发可按契约与控制面、Kubernetes 与库存、Runtime 适配、工作区与保存、Agent 接入划分交付单元；整体验收使用同一任务链，不能以单个模块编译成功替代端到端验收。
- 当前 Go 声明可独立编译，MySQL 当前 DDL 尚未按本轮版本重新执行；历史版本的建表验证不计为当前版本验收。实际 Go 最低版本、数据库最低版本和目标集群组合仍需验证。
- 主测试入口已由用户确认。本规格归属 FlyTOmeLight/agentic-kit-api，以 GitHub Issue 追踪，使用 ready-for-agent 标签进入实施队列。
