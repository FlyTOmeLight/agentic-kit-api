01 / 资产准备

先发布不可变版本，再开始对话

例子：创建“项目助手A”，配置模型、指令和授权工具。发布得到A/v1，创建Session S。之后发布A/v2，S的下一次普通聊天Run选择v2；已经接受的Run继续使用v1。场景应用可以明确指定某个VersionRef。

创建时的输入与权限如何区分？

调用方输入：名称、Config、明确AssetScope（企业共享或项目私有）。服务端核验：身份、owner、操作能力、资源绑定和项目范围。浏览器不直接提交任意工具URL或凭据绑定；受信任管理/应用入口也只能使用授权范围内的配置。

已有版本派生：CreateDerivedVersion将新资产、首个版本、来源关系与幂等结果一次提交。它的HTTP路径尚未定稿，不能把它写成已存在的路由。

02 / 完整对话

每句话形成一个Run，每个步骤都可追溯

选择步骤可查看输入、内部调用、数据库提交和失败分支；下方时序图高亮对应调用。展开完整步骤可连续阅读。

01 · 创建会话POST /v1/sessions

输入：AgentRef（AssetScope + AgentID）、可选title；身份来自认证。

处理：execution Service核验Agent读取权限和结果创建范围，保存Origin、AgentRef、ResultScope。Session不锁定某个版本。

提交：创建Session；此时没有Run，也不调用模型。

结果：返回SessionID，供后续消息复用。

分支：共享Agent可进入授权的项目私有会话；项目私有材料不能进入企业共享结果。

02 · 提交用户消息POST /v1/sessions/{id}/messages

输入：query + Idempotency-Key；可选MemorySelection、上下文政策与预算选项（目标字段语义）。

处理：认证当前主体，核验Session范围；归一Intent。缺省Memory与显式Off相同；Off不能附召回参数。

提交：还未接受Run。

结果：交给同一次提交事务。

分支：同键改query、Actor、项目或显式Memory选择属于不同意图。

03 · 查重并锁定会话durable.BindTransaction(tx).Submit

输入：标准Intent、请求命名空间及会话身份。

处理：按请求键加锁。同意图命中时直接返回原Run；新请求再锁Session，核验固定范围与活动Run。读取一次完整会话事实。

提交：尚未写入新Run。

结果：SubmissionFacts：身份、消息、来源、状态和历史截止seq。

分支：同键不同意图 → 409；同一会话已有活动Run → 409。回放仍须通过当前授权。

04 · 准备冻结材料prepare(Facts) → Spec + ContextSnapshot

输入：SubmissionFacts + 当前发布版本（聊天）或明确VersionRef（应用）。

处理：同tx读取Agent版本，编译Spec；Memory=Recall才调用RecallTx；映射规范材料，固定Policy/Budget，预检已知必需输入。这里不访问模型网络。

提交：prepare只使用同一tx与纯计算；不重复查询历史。

结果：PreparedSubmission：执行Spec + 不透明ContextSnapshot。

分支：Recall失败或预算预检失败 → 整体回滚；Recall无匹配 → Empty；Off → 不召回。

05 · 原子接受Rundurable.Submit：同一事务提交

输入：校验通过的PreparedSubmission。

处理：校验prepare返回的目标/范围与命令一致，建立Run和消息关系。首次应用任务的Session也在此事务建立。

提交：Run(Queued) + User消息 + ContextSnapshot + RunQueued事件；应用首次提交还包含Session。

结果：提交完成，任务可以被worker领取。

分支：任一写入失败全部回滚。不会留下只有消息、没有任务的半成品。

06 · 返回接受结果HTTP 202 / 200 · Submission{Run, Created}

输入：已提交的Run。

处理：首次接受返回202；同请求回放沿用200语义。Created区分新建与回放；目标响应DTO在实现时统一。

提交：无额外执行写入。

结果：客户端拿到RunID、SessionID与当前状态。

分支：丢失HTTP响应后，用相同请求键与意图重试即可找回原Run。

07 · 订阅运行事件GET /v1/runs/{id}/events

输入：RunID；可选Last-Event-ID或after，游标为runID:seq。

处理：API重新授权ResultScope与应用来源，先回放数据库事件，再等待通知或轮询新事件。

提交：不创建任务，不改变Run。

结果：SSE逐条返回事件；发送成功才推进游标。

分支：重连携带游标；WaitingClarification/NeedsReview非终态。SSE不承诺逐token输出。

08 · worker领取任务durable.Claim / Renew

输入：worker身份、领取参数；队列中的Run。

处理：Claim使用行锁与SKIP LOCKED获得Lease和新epoch；读取固定Spec、ContextSnapshot及已有checkpoint。执行期间Renew续租。

提交：Run进入Running，保存执行权及事件。

结果：只有有效Lease对应的worker可以提交执行结果。

分支：租约与Deadline均须有效；API不向某台worker派发HTTP请求，Redis也不是任务队列。

09 · 构建输入并调用模型contextbuilder.Build → Eino模型调用

输入：冻结材料 + 当前Run消息 + 实际工具定义 + 固定Policy/Budget。

处理：Eino adapter转换规范消息；Build先裁低相关Memory，再裁最旧完整历史。保留必需输入与完整当前工具链。通过后记录ModelStarted并调用模型。

提交：ModelStarted边界通过durable提交；Build本身不访问数据库。

结果：模型产生工具调用、等待交互或最终回复。

分支：必需输入仍超限 → ContextBudgetExceeded，Fail且不Retry；不截断工具正文、不调用摘要模型。

10 · 保存模型决策durable.RecordDecision

输入：模型返回的assistant消息、工具调用意图与Eino checkpoint。

处理：将模型决策转换为规范执行事实，按有效Lease提交。

提交：assistant消息、决策事件、checkpoint同事务。

结果：有工具则进入步骤执行；有最终回复则进入完成边界。

分支：API不解析Eino checkpoint；客户端Trace只看到允许公开的投影。

11 · 判断工具能否执行durable.BeginStep(StepIntent)

输入：稳定StepID、工具输入、ToolReplayPolicy。

处理：Execute：允许执行；Replay：复用保存的结果；Uncertain：不能确定上一次副作用，进入人工审核。

提交：保存或核验步骤意图与执行记录。

结果：只有Execute分支继续发起工具调用。

分支：输入或政策改变 → Conflict；Unsafe不确定结果不能自动重做。

12 · 执行工具并存档工具协议 → durable.FinishStep

输入：授权工具配置、步骤输入及可信Run/epoch执行身份。

处理：按HTTP、filesystem等真实协议调用工具；网关需要时向API检查lease。结果通过FinishStep保存，再回到Build/模型调用。

提交：工具结果、对应消息、事件及该边界的checkpoint通过durable原子提交。

结果：执行循环继续；恢复遇到同一步骤可重放已保存结果。

分支：工具执行权检查不代替业务授权；外部副作用与本地数据库不是跨系统原子事务。

13 · 完成当前Rundurable.CommitBoundary(Complete)

输入：最终output、执行状态与有效Lease。

处理：持久执行内核根据Complete边界生成合法终态和对应记录。

提交：Final消息 + Run.Completed + checkpoint/完成事件同事务。

结果：Run成为终态；后续可以接受同Session的新消息。

分支：执行失败走Fail；取消走Cancel。Completed表示框架执行完成，不保证业务目标成功。

14 · API回放与投递通知ReadEvents / OutboxRelay

输入：Run事件游标与当前授权范围。

处理：API查询事件；OutboxRelay将已提交事件通知到Redis，通知唤醒订阅读取。Redis离线则有界轮询数据库。

提交：Relay按Run事件顺序记录投递进度；不决定Run状态。

结果：API获得新增事件，准备发送SSE。

分支：不能以Redis没有消息判断Run未完成；公开Trace会截断预览，不是完整模型输入。

15 · 客户端接收结果SSE RunCompleted / RunFailed / RunCanceled

输入：已提交的事件与复合游标。

处理：客户端按事件ID去重，更新运行状态。API发送完全部已提交终态事件后结束该订阅。

提交：不修改对话事实。

结果：UI显示运行完成、失败或取消。

分支：断线只中断观察，不等于取消任务；取消必须显式调用cancel接口。

16 · 读取回复并继续对话GET messages / GET run / POST下一条messages

输入：SessionID、RunID；下一条消息使用新的请求键。

处理：GET messages读完整会话事实；GET run读输出与状态。新提交重新选择聊天默认发布版本、准备历史并独立选择Memory模式。

提交：查询不写入；新提交产生新的Run及快照。

结果：Session A可包含Run 1、Run 2……每个Run固定自己的版本和材料。

分支：发布v2不改变正在运行的v1；人工answer/resolve继续原Run，不创建下一轮Run。

03 / 两种提交入口

会话定位不同，接受Run的事务相同

每个新Run独立选择Memory
Off（默认）→不查询记忆→冻结历史与政策
显式Recall→范围 + 输出可见性校验→固定版本与完整内容

Recall无匹配保存Empty；读取失败则回滚接受事务。人工纠正记忆只影响后续新Run，首版不自动从对话提炼或写入记忆。

API与worker使用的内部调用

这些是Go能力接口，不是worker回调API的HTTP路由；durable调用最终访问共享PostgreSQL。

调用调用方向职责
Submit + prepareAPI → durable / DB请求去重、Session锁、一次Facts读取、冻结材料及原子接受
RecallTxAPI → Memory / 同tx校验记忆范围与输出可见性；返回完整版本内容
BuildAPI预检 / Worker每轮纯函数；选择材料与检查实际输入预算
Claim / RenewWorker → durable / DB领取、续租、数据库时钟、epoch与Deadline检查
CommitBoundary / RecordDecisionWorker → durable / DB类型化状态边界、消息、检查点与事件一致提交
BeginStep / FinishStepWorker → durable / DB步骤意图、Execute/Replay/Uncertain及工具结果存档
RetryWorker → durable / DB同一Run重新排队；沿用冻结配置与材料
Cancel / SupplyResultAPI → durable / DB取消或人工恢复；校验当前状态/步骤/Deadline
ReadEvents / RunSubscriptionAPI → 执行Table / 通知客户端数据库回放、游标、终态、断线重连与离线轮询
HTTP失败如何呈现？

输入非法或接受前预算超限 → 400；未认证 → 401；当前权限不足 → 403；授权范围内不存在 → 404；revision、状态或幂等冲突 → 409；外部依赖不可用 → 503。Run已接受后的执行失败通过Run状态和事件呈现，不把最初的202请求改成失败响应。
